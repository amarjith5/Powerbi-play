### 1. Creating the Semantic Model from an Existing Fact/Dimension Model

Since your underlying data is already structured into Facts and Dimensions (in SQL, a Warehouse, or a Fabric Lakehouse), your job in Power BI is **configuration and governance**, not data reshaping.

* **Choose the Right Storage Mode:**
* **Direct Lake (Fabric Lakehouse/Warehouse):** Best if your Fact/Dim tables are in Microsoft Fabric. Gives Import-level speed without data duplication or scheduled refresh delays.
* **Import Mode:** Best for high performance if your source is an external database (e.g., SQL Server) and data volume fits within capacity limits.
* **Composite / Dual Mode:** Keep Dimension tables in **Dual** mode and large Fact tables in **DirectQuery** only if near-real-time latency is mandatory.


* **Relationship Hygiene:**
* Enforce **1-to-Many ($1:*$)** single-direction relationships from Dimension (1) to Fact ($*$).
* **Avoid bi-directional cross-filtering** unless strictly required for a specific bridge table—it degrades performance and confuses Copilot.
* For **Role-Playing Dimensions** (e.g., `Order Date`, `Ship Date`, `Delivery Date` all pointing to one `Dim_Date` table), keep one active relationship and activate the others on-demand inside measures using `USERELATIONSHIP()`.


* **Dedicated Measure Table:** Create an empty table (e.g., `_Key Measures`) with display folders (`Sales`, `Margin`, `YoY Time Intelligence`) to house all explicit DAX measures and keep Fact tables clean.
* **Key Gotcha:** **Disable "Auto Date/Time"** in Power BI Options immediately. Leaving it on creates hidden date tables for every single date column across your Fact/Dim tables, bloating model size and confusing Copilot.

---

### 2. Standard Operating Procedure (SOP): Excel-to-Power BI Migration Document

Instead of developers converting reports ad-hoc, publish a 5-step **"Excel-to-Power BI Playbook"** that every developer must follow:

1. **Deconstruct & Map (The "No 1:1 Lift" Rule):**
* Document every tab in the Excel file: Is it a *Raw Data dump*, a *Calculation/Lookup staging tab*, or a *Presentation output*?
* **Rule:** Never recreate staging/lookup tabs inside Power BI. Only recreate the final business logic and presentation layer.


2. **Logic Translation Matrix:**
* `VLOOKUP` / `XLOOKUP` / `INDEX-MATCH` $\rightarrow$ Replaced by **Star Schema Relationships** (or merged upstream in SQL/Dataflows if combining two dimensions).
* `SUMIFS` / `COUNTIFS` $\rightarrow$ Replaced by **DAX `CALCULATE()**` measures with filter predicates.
* Cell-by-cell hardcodes / manual overrides $\rightarrow$ Moved to a governed **SharePoint/SQL reference table** ingested into the model.
* VBA Macros used for data formatting $\rightarrow$ Replaced by **Power Query / Fabric Pipelines**.
* Wide 40-column printable Excel tables $\rightarrow$ Routed to **Power BI Paginated Reports (`.rdl`)**, *not* standard Power BI canvas visuals.


3. **Golden Dataset Binding:**
* Developers must **not** create a new `.pbix` with its own data model for each report. They must open Power BI Desktop and connect via **Live Connection** to one of your 5–10 governed Semantic Models (**Thin Reports**).


4. **Parallel Run & UAT Sign-Off:**
* Run the legacy Excel report and new Power BI report side-by-side for **2 historical reporting cycles**. Sign-off requires $<0.01\%$ variance on core KPIs.

### 3. Sending Daily Email Notifications to 100+ Users

When sending automated daily reports to 100+ users, how you architect it depends on licensing, security (RLS), and whether each user needs a customized view.

| Approach | Best For | Pros | Cons / Limits |
| --- | --- | --- | --- |
| **Option A: Standard Power BI Email Subscriptions (with AD Security Group)** | All 100+ users receive the **same default view** (or have RLS applied automatically when viewing) | Zero code; takes 2 minutes to set up; respects **Row-Level Security (RLS)** automatically for standard Power BI reports. | Max 24 subscriptions per report; best to put all 100+ users into **one Microsoft Entra (Azure AD) Security Group** and subscribe the group. |
| **Option B: Dynamic Per-Recipient Subscriptions (Fabric / Premium)** | Each of the 100+ users needs a **personalized PDF/attachment filtered to their specific Region/Store** | Data-driven: pulls recipient emails and their filter parameters (`Region = South`) directly from a table in your Semantic Model. | Requires **Fabric Capacity (F64+)** or **Power BI Premium (P1+)**; max 1,000 recipients per dynamic subscription. |
| **Option C: Power Automate (`Export to File` Flow)** | Custom email HTML bodies, conditional alerts (e.g., *"Only send if Sales drop $>10\%$"*), or saving PDFs to SharePoint | Total control over email formatting, scheduling, and conditional logic. | **API Throttling Pitfall:** The `Export to File for Power BI Reports` connector has strict concurrency limits. Looping 100 individual PDF exports will fail or throttle unless queued or batched. |

* **Best Practice Recommendation for 100+ Users:**
* If they all share the same security role or you use **RLS** on the semantic model, put the 100+ users into a **Microsoft Entra Mail-Enabled Security Group** and set up **one Standard Subscription** with *"Include link to report"* and *"Report page preview."*
* If they do not want to click into Power BI and demand a **multi-page table attachment** in their inbox at 8:00 AM, build a **Paginated Report** and use a **Dynamic Subscription** (or bursts via Power Automate).

### 5. Deployment Through Pipelines (Dev $\rightarrow$ Test $\rightarrow$ Prod)

Never publish directly from a developer's laptop to the Production workspace. Use **Fabric / Power BI Deployment Pipelines** paired with **Git Integration**:

```
[Developer PBIP + Git] ──► [DEV Workspace] ──► [TEST (UAT) Workspace] ──► [PROD Workspace] ──► [Power BI App]

```

* **Step 1: Decouple Models from Reports (Workspace Architecture):**
* **Option 1 (Single Pipeline):** Keep the shared Semantic Models and Thin Reports in the same pipeline, but use **Selective Deployment** so updating 1 report doesn't redeploy all 90 reports.
* **Option 2 (Enterprise Split):** Put your 5–10 **Semantic Models** in a dedicated *Data Workspace Pipeline* and your **Thin Reports** in *Domain Report Pipelines* connected via cross-workspace permissions.


* **Step 2: Configure Deployment Rules (Critical!):**
* Inside the Deployment Pipeline UI, set **Data Source Rules** and **Parameter Rules** on the Semantic Models:
* `DEV` points to `Dev_Lakehouse / Dev_SQL`
* `TEST` points to `UAT_Lakehouse / UAT_SQL`
* `PROD` points to `Prod_Lakehouse / Prod_SQL`




* **Step 3: Use the `.pbip` (Power BI Project) Format + Git:**
* Save files as **`.pbip` (TMDL / PBIR format)** instead of binary `.pbix` files. This saves your Semantic Model and Reports as human-readable text files in Azure DevOps or GitHub, allowing multiple developers to work on the 90-report migration simultaneously without overwriting each other's work.


* **Step 4: Distribute via Power BI Organizational Apps (Audiences):**
* In the `PROD` workspace, do **not** grant the 100+ end users direct workspace access. Publish a **Power BI App** and use **App Audience Groups** (e.g., *Executive Audience*, *Finance Audience*, *Store Managers Audience*) to control who sees which of the 90 reports in a single clean navigation menu.

### Summary of Top Project Risks to Watch Out For

1. **The "Thick Report" Trap:** If developers import data directly into 90 separate `.pbix` files instead of using **Live Connections (Thin Reports)** to your shared Fact/Dim Semantic Models, your Fabric/Power BI capacity CPU and memory will crash under 90 daily refreshes.
2. **Email Subscription Sprawl:** Do not add 100 individual email addresses manually to 90 reports—when someone leaves the company or changes roles, updating 90 subscriptions manually is a nightmare. Always use **Entra ID Security/Distribution Groups** or a **Data-Driven Subscription table**.
3. **RLS + Caching Conflict in Subscriptions:** If you use Row-Level Security (RLS) on the Semantic Model, make sure the service account or user triggering a Power Automate PDF export doesn't accidentally email an unfiltered "All Regions" PDF to a regional manager. Standard Power BI Subscriptions natively enforce the recipient's RLS role; custom Power Automate flows require explicit `effectiveIdentity` configuration in the API payload.
